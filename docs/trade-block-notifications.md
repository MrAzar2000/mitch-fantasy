Trade block notifications are queued and delivered once at 9:30 pm America/New_York, automatically adjusting for daylight saving time. A day without additions sends no push. Additions after the cutoff are included in the following night's digest. Both shopping and open-to-offers players count; switching a player between those statuses, changing needs or notes, and removing players do not count. Repeated delivery of the same webhook is deduplicated.

Activation requires the existing Supabase sender and Netlify queue to use the same shared notification secret. Configure `NOTIFY_SECRET` in Netlify's Functions runtime using the existing sender's secret, and set `TRADE_DIGEST_NOTIFY_URL` to the existing Supabase notify function's HTTPS URL. Keep secret values out of source control. Deploy the Netlify changes before updating the Supabase function.

In Supabase, run `ALTER TABLE public.trade_block REPLICA IDENTITY FULL;` so UPDATE database webhooks include the previous listing. Keep the existing INSERT/UPDATE webhook to the notify function, including its authentication header. Deploy the updated `supabase/functions/notify/index.ts` using the project's normal Supabase deployment process. This switches trade webhooks from immediate pushes to the Netlify queue; league announcements and other direct notifications retain their behavior. Netlify deployment alone does not update the Supabase function or its database configuration.

Check an UPDATE webhook includes `old_record.listing` before enabling the new sender. The queue rejects updates missing that history rather than treating every edit as an addition. Confirm a new player produces a pending database entry without an immediate push, then verify the published site's scheduled digest at 9:30 pm Eastern. Netlify schedules run only on published production deploys.

Delivery uses a daily database marker and a transaction lock to suppress repeat or overlapping runs. An unsuccessful send keeps additions pending for a later nightly run. As with any push provider, a process crash after provider acceptance but before database commit, or a partial provider failure, can lead to repeated delivery on a later attempt. Existing listings are not backfilled as new additions.

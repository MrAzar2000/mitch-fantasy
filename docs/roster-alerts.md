# Roster alerts and recovery

The published Netlify site checks roster alerts every 15 minutes. It uses the existing Supabase notify function as an authenticated source of the public league snapshot and as the push sender. Deploy the included update to `supabase/functions/notify/index.ts` through the existing Supabase deployment process; deploying the Netlify site alone does not update that function. The sender advertises roster-alert and remote-test support, and the Netlify functions refuse to use older senders. The existing `NOTIFY_SECRET` and `TRADE_DIGEST_NOTIFY_URL` configuration is reused; no new credentials are required.

Apply the new forward-only `20261023180000_create_roster_alert_deliveries` migration through the normal Netlify deployment flow. Existing applied migrations were preserved. Netlify scheduled functions run on published production deploys, not Deploy Previews.

Unavailable starter warnings cover OUT, doubtful, injured reserve, suspension, and current-week byes. They are sent only within 24 hours of a known future kickoff. Bench players and already locked players do not trigger injury alerts. A lineup reminder is sent within an hour of the next known starting-player kickoff, at most once per team per scoring week. Empty-slot counts are included only when ESPN confirms starting-slot settings. Unknown kickoff times, inconsistent scoring weeks, and league snapshots older than 15 minutes suppress advice. No waiver processing time is invented when the league feed does not provide a reliable deadline.

Alerts target subscribers for the affected team. They use the existing matchup category and honor categories and quiet hours. If the preference service is unavailable, the sender now returns an error rather than bypassing saved preferences. Suppressed delivery counts as a completed attempt so alerts do not arrive late after quiet hours. Delivery markers and transaction locks suppress repeated and overlapping schedule executions. As with other existing push delivery, provider acceptance followed by a process crash before commit, or partial provider failure, can cause a repeated attempt; stable notification tags limit duplicate visible notifications.

The notification settings test now sends a real remote push to the requesting browser's saved subscription. It requires a saved subscription hash and permits one test attempt per browser per minute. It reports suppression, missing subscriptions, and unsupported senders without claiming successful physical-device delivery.

Offline recovery caches the app shell and the last successful public league response in browser Cache Storage. It requires a previous successful visit and supported browser storage. A saved view always displays its source timestamp and a stale-data banner. Lineup and pickup recommendations are paused, and transactional pages require reconnection. No writes are queued. A successful online league check reloads a saved view to revalidate all data. API responses, subscription endpoints, credentials, and user submissions are not stored in the shell cache. Storage denial leaves the existing retry experience available.
